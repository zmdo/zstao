# 提示词写法

提示词不是咒语，是把「要求」写成对方能执行、你能验收的形式。

## 六段式结构

```text
【角色】以什么身份、什么标准回答
【目标】要产出什么，一句话说完
【上下文】相关文件、已有结论、硬约束
【做法】必须遵守的步骤；明确不能做什么
【输出】格式、长度、语言、文件路径
【验收】什么情况下算合格
```

六段里最容易省略、也最不能省的是【验收】。没有验收标准，输出只能靠感觉判断。

## 变量约定

可复用提示词里的可变部分统一写成 `{{变量名}}`，使用前全部替换。

| 变量 | 含义 | 示例 |
| --- | --- | --- |
| `{{目标}}` | 本次要交付的东西 | 评审 `feat/login` 分支的改动 |
| `{{上下文}}` | 相关文件、背景 | `src/auth/`、`docs/decisions/0003.md` |
| `{{约束}}` | 不能违反的硬条件 | 不改数据库 schema |
| `{{输出格式}}` | 期望的结构 | 按严重度排序的表格 |

## 一个例子

**弱**：

```text
帮我看看这段代码有没有问题。
```

**强**：

```text
【角色】你是一名严格的代码评审者，只评审本次 diff。
【目标】判断这次改动能否合并。
【上下文】diff 见下方；服务是支付回调，错误处理必须幂等。
【做法】只评审改动行及其直接影响；不臆测未读代码；不重写实现。
【输出】Markdown 表格：严重度 | 文件:行 | 问题 | 建议。先给一句结论：通过 / 有条件通过 / 打回。
【验收】每个阻塞项都能指出对应的验收条件或风险；没有证据的猜测单独列为「疑问」。
```

差别不在篇幅，而在于：弱提示词把判断标准留给了自己，强提示词把它交给了对方。

## 反模式

| 反模式 | 后果 | 改法 |
| --- | --- | --- |
| 堆形容词（「专业」「高质量」） | 无法执行，也无法验收 | 换成可检查的条件 |
| 一次塞多个目标 | 每件事都做一半 | 一个提示词只做一件事 |
| 只给目标不给上下文 | 输出泛泛而谈 | 附文件、结论、约束 |
| 不指定输出格式 | 每次都要重新整理 | 给出模板或表格结构 |
| 用聊天记录代替仓库 | 上下文丢失、无法复现 | 把结论落进文件，再让 AI 读文件 |

## 维护

- 一个文件一个用途，文件名即用途。
- 修改前先在 `work/` 里记录为什么改。
- 新增提示词后在 [`prompts/README.md`](../prompts/README.md) 登记。
