# 应用服务器自动注入 TCR 凭据（简化版）

状态：已实现，待部署验收。分支：`codex/application-server-tcr-simple`。

本分支从 `911443e` 创建。`08f3947` 的复杂方案及其所在分支保留，不重写 Git 历史。已确认 `08f3947` 在线上部署并执行过 `0047` 数据库迁移，因此通过新的 `0048` 迁移清理旧方案，而不是直接回退线上代码。

## 使用方式

1. 在现有“项目镜像仓库”设置中填写 Registry、命名空间、用户名、密码，勾选“允许向应用服务器分发此账号”。请在 TCR 中将此账号限制为所需仓库的拉取权限。开关默认关闭，旧配置不会被直接分发。构建端继续使用自己的推送凭据。
2. 登记服务器时选择“应用服务器”，系统自动创建类型准备任务。已有服务器通过现有类型切换流程选择该类型。
3. 系统检查 Docker Engine 和 Compose。允许安装缺失软件时，先按现有安装计划安装，再注入；未允许安装且软件缺失时，任务失败，不发送凭据。
4. Docker 就绪后，执行 `docker login --password-stdin`。任务记录显示成功或可重试的类型配置错误。
5. 密码更新后保存镜像仓库设置，对已有应用服务器执行“安装组件”，重新检查并注入当前密码。Docker 已就绪时不会重复安装。

TCR 管理 API 的 SecretId/SecretKey 和 Docker 用户名/密码分别配置。保存拉取凭据不要求配置或连通 TCR 管理 API。“测试 TCR API”只验证管理 API；类型准备任务验证 Docker 登录，具体镜像的读取权限由实际 `docker pull` 验证。

关闭分发开关只阻止后续注入，不会远程撤销已发出的凭据。需要撤销时，在 TCR 撤销账号权限或更换密码，并清理服务器配置。

## 拉取与部署

注入在选择类型后的准备阶段发生。第一次、第二次和后续拉取均读取服务器上的同一份 Docker 配置，不再向 CES 请求凭据。不存在首次拉取回调、凭据版本表、周期同步或部署调用 Token。

配置位置为 `/var/lib/ces/application-server/docker/config.json`，目录权限 `700`、文件权限 `600`，由 root 持有。普通 `docker pull` 不会自动搜索此专用目录；使用以下方式：

```sh
sudo docker --config /var/lib/ces/application-server/docker pull <registry>/<namespace>/<image>@sha256:<digest>
sudo docker --config /var/lib/ces/application-server/docker compose -f compose.yml up -d
```

项目现有 `deploy/ces-runtime.sh` 会优先使用这个目录；显式设置 `DOCKER_CONFIG` 时遵从该设置，没有新配置时沿用 `/srv/ces-prod/docker-config`。拉取失败会在删除当前容器之前返回失败。

AI 会话中的流程：修改项目代码 → 提交到项目仓库 → 由现有 OneDev 构建任务构建并推送镜像 → 获取镜像 digest → 通过现有 SSH/发布脚本在应用服务器拉取并启动。镜像由项目现有构建执行环境构建，本方案不新增构建服务器、不在应用服务器安装构建 Agent，也不新增部署 API。

## 实现与保留范围

保留应用服务器类型、Docker/Compose 定义、已有 SSH 管理、软件安装计划、任务记录与类型切换流程。

服务器类型只增加 `requiresSetup` 元数据及主机端准备回调。回调在现有任务中执行，受现有任务租约和远端执行锁约束。正常巡检不运行准备回调。软件安装恢复成功后也需要执行准备回调，才报告最终成功。类型切换先完成目标配置，再清理原类型配置，最后提交绑定；失败由原任务报告。

凭据执行时从现有加密的 `image-registry.json` 读取，经 SSH 标准输入传给登录程序，不进入类型快照、计划、远端安装日志或任务结果。Docker 输出被丢弃，调用失败只报告不含凭据的错误。成功登录后原子替换配置；登录失败保留旧配置。远端 Docker 配置中的认证内容不是加密存储，文件权限用于限制读取。

切换离开应用服务器类型时，仅删除本插件专用的 `config.json`，保留其他 Docker 配置和现有容器。仅删除 CES 中的服务器登记不会执行远端清理；下线前应先切换类型，或者由管理员清理专用配置并撤销账号权限。

不保留 `08f3947` 的通用 configure 任务、凭据版本与绑定表、后台对账、部署调用方 Token、拉取回执及新增 CI 部署接口。

## 已部署数据库的清理

迁移文件：`plugins/database/migrations/0048_cleanup_legacy_registry_credentials.sql`。

删除范围：

| 对象 | 处理 |
| --- | --- |
| `application_registry_requests` | 删除旧调用请求、回执及表 |
| `application_registry_bindings` | 删除旧凭据绑定、同步状态及表 |
| `application_registry_clients` | 删除旧调用方 Token 哈希、授权范围及表 |
| `server_configuration_sequence` | 删除旧 configure 序列 |
| `server_jobs` | 只删除 `purpose=configure` 且 `operation=@smp/console-application-server/registry-credentials` 的任务，包括旧托管部署任务 |
| `server_job_steps` | 通过已有外键删除上述任务的步骤 |
| `server_jobs_purpose_check` | 恢复为 inspect、detect_updates、apply_plan |

保留服务器、分组、SSH 密钥、普通任务与安装计划、其他插件数据以及 `console_schema_migrations` 的历史记录，包括 `0047`。新分支不包含可重新创建旧表的 `0047` 生产迁移文件；测试夹具中的同名文件不会由迁移器执行。

迁移由已有运行器在一个事务内执行，并对任务表加锁。以下情况会中止并回滚：

- 存在 claimed、running 或 recovering 的旧 configure 任务，即便租约已过期。
- 存在不属于上述旧 TCR 操作的 configure 任务。
- 删除对象存在意外依赖，或者不能在 5 秒内获得所需锁。

不使用 `DROP ... CASCADE`。支持旧对象不存在的新安装；重复执行不改变保留数据。中止后应在旧版本核对并完成/结束对应远端操作，再重新升级，不要直接删除运行中任务或修改迁移历史来绕过检查。

## 上线顺序与回退

1. 暂停旧 CI 部署入口和旧后台任务的新增工作，使用旧版本核对并处理未完成操作。停止所有旧 CES 实例，避免旧程序继续写入旧表。
2. 备份数据库、DSH 配置目录和必要的远端发布配置。保留旧镜像及对应代码。
3. 部署本分支构建的新版本，由现有迁移器执行 `0048`。迁移失败时先排查错误，数据库删除操作会随事务回滚。
4. 从本分支更新发布脚本和项目构建配置，停止使用 `08f3947` 新增的 CI Token / 托管部署接口。本分支沿用原有 OneDev 构建和 SSH 发布流程。
5. 在镜像仓库设置中确认拉取账号并开启分发。对已经登记的应用服务器执行一次“安装组件”，确认任务成功，再实际拉取一个有权限的镜像 digest。既有服务器不会在升级启动时自动批量重写凭据。
6. 验收通过后恢复构建与部署。

`0048` 成功后，如果要回到 `08f3947`，必须恢复迁移前数据库备份并匹配旧配置、旧程序；仅换回旧镜像或执行 Git 回退不能恢复已删除的数据。项目现有发布脚本的容器回滚不负责恢复数据库，执行本次升级时必须按上述流程处理数据库备份/恢复。

数据库清理不会删除旧 `$DSH_HOME/registry-pull-credentials.json`，也不会连接远端删除旧 `/var/lib/ces/docker-config/platform-pull` 等配置目录。它们与新版配置独立；新版验收后应先核对使用方和回退需求，再清理旧文件并撤销不再使用的凭据。本次开发没有连接线上执行删除。
